# Modifications for the web

Assignment 2's runtime in `explorer/`, `lm/`, `models/`, `data/` and `reports/` is copied unchanged from
commit `aa56a26` (tag `v1.0`) by `tools/vendor_a2.py`; `A2_VENDOR.json` holds the SHA-256 of every file and
`tests/test_vendor_integrity.py` recomputes them. Every change made for the web is in `app/` or is listed
here, with the test that covers it. Numbers refer to plan section 7.5.

| No. | Modification | Why | Test |
|-----|--------------|-----|------|
| (config) | `config/settings.json` gains a `web` block (what-if limits, list sizes, time limits, chart, watchlist and live-lookup limits, replay speeds, request limits). Every other key is Assignment 2's, unchanged | The web tier needs numbers of its own, and the front end reads them from `GET /api/config`, so the tiers cannot disagree | `test_vendor_integrity.py::test_settings_json_differs_from_assignment_2_only_by_the_web_block`; `test_config.py` |
| Mod-1 | The Predictor loads once, in the background during the application's lifespan, and is shared read-only. `GET /api/health` answers 503 until it is loaded | A load takes about a second; a request must not pay it, and the front end must be able to tell "starting" from "down" | `test_system_api.py::test_health_is_503_while_the_models_load_then_200`; health reports the counts |
| Mod-2 | `services/explorer_service.py` keeps a per-address cache of `score_address`'s result, one entry per (method, address), least recently used leaving first, as many entries as there are snapshot addresses (28). It fills lazily and is warmed for all 28 addresses under the default method in a background thread once the service is ready (about 1.2 s, about 50 MB) | Repeat views answer from memory (E5 1.5 ms warm against 57 to 102 ms cold) | `test_cache.py` (second view served from the cache and equal; least-recently-used eviction; warm-up after ready) |
| Mod-3 | `score_address`'s single result (up to 2 MB) is cut into the timeline (E5), a filtered, sorted, paged list of rows (E6) and one transaction (E7) | A view needs a few kB: the timeline is 11 to 18 kB, a page of 200 rows 52 kB, a transaction under 3 kB | `test_parity.py`: for all 28 addresses E5, E6 and E7 rebuild exactly what `score_address` returns |
| Mod-4 | An address with too little history gets a timeline and rows built from the feature table, all unscored; a transaction that could not be scored answers 422 with its facts and how much history lay behind it | `score_address` raises for these addresses, but the screen lists their transactions unscored | `test_parity.py::test_a_short_history_address_...`, `test_explorer_api.py` (E5, E6, E7 for the three short-history addresses) |
| Mod-5 | `services/whatif_batch.py` builds the features of many hypothetical transactions (one address, one time, many amounts) in one `build_features` call and scores them with the methods that can score new input; E9 uses it, E8 stays `Predictor.score_what_if` as it is. The hypothetical row is built the way `score_what_if` builds it | A curve of 41 amounts called one by one would take about 12 s (0.3 s each); one build takes about 0.2 s. Same-time transactions are never each other's history, so the rows do not see one another and each sees exactly what a single call would give it | `test_whatif_parity.py`: every method's score and flag equal a single call over six addresses, both directions, three times each (a full run compares all 41 amounts of every curve); two planted off-by-one bugs and a staggered-time bug are shown to fail it |
| Mod-6 | A what-if that cannot be scored answers 422 with the history counts and the first day that could be scored, both when no transaction is earlier (A2 raises) and when some are but under the minimum (A2 returns the row unscored). A time more than `web.whatIf.maxGapYears` after the last transaction answers 400 | A1's meaning of 422; the form can say which date would work | `test_whatif_api.py` (early-time what-if, short-history addresses, the 400 for a time too far ahead) |
| Mod-7 | `method=` (E3, E5, E6, E7) gives the request a `Predictor` that shares the loaded tables and differs in `selected` (`dataclasses.replace`) | S-01: the deciding method is the user's choice | `test_parity.py::test_each_methods_flags_equal_scores_csv` (nine methods) |
| (http) | `ETag` and `Cache-Control: no-cache` on snapshot GETs, E2 `/api/config` included, with 304 on a matching `If-None-Match` (`core/middleware.py`, switched on per route by `api/deps.py::snapshot_data`); a body over `web.limits.maxBodyBytes` answers 413 (`core/body_limit.py`) | Plan sections 6.1 and 6.3: a repeat request costs a 304; a body over 10 kB is refused before it is parsed | `test_http_layer.py` |
| Mod-8 | `Unsupported` becomes 404, `InsufficientHistory` 422, `ValueError` 400 and a missing file 503, in `app/core/errors.py` and nowhere else; validation errors answer 400 instead of FastAPI's 422 | One error body, and Assignment 1's meaning of 422 | `test_errors.py`, one test per mapping |
| Mod-12 | `services/reasons.py` rewrites two things in the text Assignment 2's `explain.py` produces, wherever the services pass it on (E6 `mainReason`, E7 and E8 `explanation`, and so E10). (a) Wording: F4's two headlines, "Higher ratio to the usual amount than usual" and "Lower ratio to the usual amount than usual", become "Larger amount relative to the usual for this direction" and "Smaller amount relative to the usual for this direction". The six headlines of F1 to F3 already read well and are unchanged. (b) Amounts: every `N BTC` in the text is written with eight decimals ("0.0011126 BTC" becomes "0.00111260 BTC", "0.05 BTC" becomes "0.05000000 BTC") | A2's F4 headlines repeat themselves; its `format_btc` strips trailing zeros, so the explanation disagreed with the screen's eight-place amounts. The mapping is keyed by A2's own `headline()` and checked against the wording rule when the module loads | `test_reasons.py` (every phrase A2 can produce and what it becomes; amounts, including that E7's text equals its facts to the satoshi); `test_parity.py` (rows and details equal A2's, reworded) |
| Mod-13 | A 400 names every field at fault across both layers. Pydantic stops at type faults, so `core/errors.py::handle_validation` then applies the route's service rules (`api/field_rules.py` to `ExplorerService.rejected_query`, `WhatIfService.rejected_what_if` and `rejected_curve`) to the values that did pass their type check. A value that failed its type check is not judged again. `Amount` now carries its own reader, so one raw value can be judged exactly as a body field is | `?pageSize=999&status=bogus` reported only `status`; `amountsBtc: [0.01, 0, 0.02, 1e-9]` reported only the `0` | `test_explorer_api.py` and `test_whatif_api.py` (both examples, and mixed faults on E6, E8, E9) |
| Mod-14 | E6 and E10 `sort=amount` orders by the size of the net amount (`abs(netSats)`), not the signed value; `-amount` is largest first; equal sizes stay oldest first | Signed order listed every received transaction before any sent one when sorting "largest first" | `test_explorer_api.py` (`test_e6_sorts`, the mixed-direction check), `test_export_api.py` (E10 equals E6 for `sort=amount` and `-amount`) |
